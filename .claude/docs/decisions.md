# Decisions

What is decided and why, and what is still open. A decision on an open question is recorded here
in the same change that acts on it. Locked decisions are summarised in [CLAUDE.md](../../CLAUDE.md);
changing one is a large change.

## Decided

| Decision | Reason |
| --- | --- |
| One owner; the control bot answers only `OWNER_TELEGRAM_ID` | The product controls a real account; one trusted user keeps the permission model trivial |
| The owner likes in the matching bot by hand; the system never touches it | Automating a matching bot risks that account and removes the owner's judgment at the first step |
| Automatic replies only to `active` contacts, checked at scheduling and again before sending | Statuses change while a delayed job waits; a single check is not enough |
| Every outgoing message goes through the sender | One place for the guard, limits and pacing; they cannot be bypassed |
| Stop-triggers hand over: meeting or date, phone and contact exchange, money, photo requests, direct bot or AI question, low model confidence | These are the moments where a wrong answer costs the owner something real |
| Style from persona text plus few-shot examples from the owner's real chats; modes are a prompt fragment plus examples; no model training | Cheap to change, no training data pipeline, no model hosting |
| One LLM interface, DeepSeek first over plain httpx, provider replaceable by config | Avoids lock-in to an SDK; a single HTTP client is easy to fake in tests |
| PostgreSQL, async SQLAlchemy 2.0, Alembic, Redis, Arq, Docker Compose, uv | One async stack end to end; Arq needs Redis; Alembic keeps schema changes reviewable |
| Real personal data never goes to git; fixtures use fake data | The data belongs to real people |
| No message text, names or personal data in logs at INFO or above | Logs get copied and shipped; content must not travel with them |
| Python 3.14 (`requires-python >=3.14,<3.15`, `.python-version`, `python:3.14-slim-bookworm`) | One interpreter version in local runs, Docker and CI |
| Redis runs with AOF on a named volume | Arq's delayed jobs live in Redis and must survive restarts |
| Compose builds `DATABASE_URL` and `REDIS_URL` from `POSTGRES_*` and the service names | One source of truth for credentials; the same `.env` works locally and in Docker |
| `docker-compose.override.yml` publishes Postgres and Redis on `127.0.0.1` only | Host access for `psql` and a local app without exposing the services to other machines |
| `docker-compose.override.yml` bind-mounts `./data/media` over `/data/media` in `app` and `worker`; production (`docker-compose.yml` alone) keeps the named `media` volume | Collected photos are visible in the project folder without copying them out of the Docker VM |
| `postgres:16.15-alpine` and `redis:7.4-alpine`, pinned by tag | Reproducible builds; Dependabot proposes bumps |
| Dependabot runs weekly for GitHub Actions, Docker, Docker Compose and uv | Pinned versions stay current without manual tracking |
| JSON logs to stdout, with Arq's own lines in the same format | One format for every process; the container runtime collects stdout |
| Heartbeat file for the app healthcheck; `arq --check` for the worker | The app has no HTTP server; Arq already ships a check |
| The healthcheck entry point (`cyrano.health`) reads `HEARTBEAT_PATH` from `os.environ` itself instead of `Settings`: the one exception to hard rule 3 | The module stays stdlib-only, so the check starts fast and imports nothing heavy (no pydantic, no application config); it reads that one variable and nothing else |
| The startup log line carries an allowlist of settings (`LOGGED_SETTINGS`), not everything that is not a secret | A new setting is not logged until someone adds it on purpose; Telegram ids and the session path can identify a person |
| Timestamps are `timestamptz` stored in UTC; `TIMEZONE` applied only at the edges | Avoids offset bugs in stored data |
| Migrations run in a one-shot compose service `migrate`; `app` and `worker` wait for `service_completed_successfully` | A failed migration stops the start instead of running new code on an old schema; app and worker never race each other to migrate |
| `alembic.ini` and `migrations/` live at the repository root; `env.py` is async and reads `Settings.database_url` | One driver, one source of truth for the URL, no credentials in a config file |
| `MetaData` has a naming convention | Constraint and index names are stable, so later migrations can refer to them |
| Revisions repeat table names and enum values as literals instead of importing them | A revision records the past and must not change when the code does; `alembic check` and a test catch disagreement |
| Status transitions as in [contact-lifecycle.md](contact-lifecycle.md), data plus one function in `domain/transitions.py` | One place for the rule; every other layer calls it |
| Requesting the current status is a no-op, not an error | A repeated button press or event is harmless and must not raise |
| `ignored` is terminal | The owner said no; "silence forever" must not be undone by mistake |
| A contact becomes `active` only with a mode | A reply cannot be built without a mode |
| A disabled or missing mode falls back to `default`; a missing or disabled `default` raises | Disabling a mode must not silence its contacts; when no style is available the safe result is no reply |
| Repositories are `Protocol`s in `services`, SQLAlchemy implementations in `db`, returning domain models | Services stay independent of the ORM; `db` never imports `services` |
| Every repository method is one transaction | Simple and enough for today's callers; nothing needs a wider transaction yet |
| Database tests run on real PostgreSQL, one fresh database per test, migrated by Alembic; unreachable Postgres fails the test | JSONB and native enums behave differently on anything else; a skipped test proves nothing |
| `TEST_DATABASE_URL` stays out of `Settings`; tests read it themselves from the environment or `.env` | The application must not know about a test database or require the variable in production |
| Dependencies added for storage: `sqlalchemy[asyncio]`, `asyncpg`, `alembic` | Agreed for CYR-9; together they are the stack already decided above |
| Dependency added for the userbot: `telethon` (1.45.0 at the time of CYR-10), imported only inside `userbot/`, typed through Protocols with a per-module mypy override (`ignore_missing_imports`) | Agreed for CYR-10; it ships no type information, and the Protocols keep our code free of `Any` and testable with fakes |
| `NewContactEvent` is best-effort; the database is the source of truth | A lost event must not lose a contact. Contacts in status `new` are in the database whether or not their event was delivered, so CYR-12 can always find them |
| A bounded in-memory queue (1000) carries the events; a full queue drops the new event and logs a warning with counters | Intake must never block or fail because a consumer is slow or missing. The profile collector consumes it (CYR-11) |
| A contact is registered on any private message from a real user, media-only messages included; the text is the caption or an empty string; media is not downloaded | The owner has to see everyone who wrote. `messages.text` allows an empty string, so no placeholder is needed. Downloads belong to a later ticket |
| NUL bytes are removed from text, username and display name before any repository call | PostgreSQL rejects NUL in text and JSONB; otherwise one such message would fail every redelivery of itself |
| Two simultaneous first messages are resolved by get-after-conflict: the loser of `create` reads the contact by `tg_id` and continues as for a known sender | The unique `tg_id` already arbitrates; no extra lock or retry loop. Exactly one call created the contact, so exactly one event is published |
| Catch-up on every start: the client is built with `catch_up=True` and `catch_up()` is called after connect | Messages that arrived while the app was down are processed. Calling `catch_up()` alone would not load the update state saved in the session. Idempotency makes replays safe |
| The handler is registered before the client connects | No update can arrive at a client without a handler |
| The app exits at once with "run `make login`" when the session file is missing, before any client exists; an unauthorized session and a 30 s connect timeout are readable fatal errors too; normal startup never prompts | A restart loop must never hang, prompt for input or touch the network without a session. The restart policy handles the rest |
| An unexpected disconnect ends the process with an error | Telethon already retries; when it gives up, a restart is the honest recovery, and the restart policy provides it |
| The handler retries the intake call: 3 attempts in total, 1 s then 2 s apart, for any exception except `asyncio.CancelledError`; after the last attempt it logs an error with the class name and counters and drops the message | A transient failure (a database blip) should not lose a message. Intake is idempotent (message append on `(contact_id, tg_message_id)`, contact creation by get-after-conflict), so a repeat is safe. Updates are sequential, so a retry delays the next update by a few seconds; accepted. Limit: a failure after the contact was created but before its event was published still loses the event (events are best-effort) |
| SIGTERM and SIGINT during startup end it at once: the connect and the catch-up are each raced against the stop event, the 30 s connect timeout stays for the real timeout case | The connect timeout is longer than Docker's 10 s grace period, so waiting it out meant SIGKILL. A stop request must give a clean shutdown (handler removed, client closed, engine disposed, exit 0) in about a second |
| The profile collector consumes `NewContactEvent` first; the card (CYR-12) starts from `ContactReadyEvent` | Answers the earlier open question about the order of consumers. The card must show nick, bio, photo and the matching-bot text, so something has to collect them before the card, and the card must not poll the database |
| `ContactReadyEvent(contact_id)` means "collection finished, successfully or not, the card may be shown" and is published in a `finally` for every attempted contact | The card must never wait forever for a profile that Telegram refuses to give. The consumer shows what is there. Nothing consumes it yet (CYR-12); it is a second in-memory queue of the same generic class as the first |
| The in-memory event queue is generic over the event type (`InMemoryContactEvents[T]`, `ContactEventPublisher[T]`) | Two event types, one implementation, no `Any` |
| Collection is strictly sequential: one event, one contact at a time | Gentle on Telegram limits (account limits and bans are a main risk); the owner likes profiles by hand, so the volume is low and parallelism buys nothing |
| The three parts (Telegram profile, photo, Leomatch lookup) run independently, each in its own `try/except`, under one 30 s budget per contact (`asyncio.wait_for`) | A privacy-restricted photo or a missing matching-bot chat must not cost the owner the bio. A hanging call must not block every later contact. What was gathered before the budget ran out is still stored |
| `LeomatchProfile.raw_text` is the card text only and may be empty; the match message text goes to its own field `match_text` and is never shown as profile text or parsed for fields. Name, age, city and about are filled only when the card text matches the observed card format | Before CYR-33 `raw_text` fell back to the match text, so a missed card showed the congratulation under the profile-text label. Parts of the format are still unobserved (see open questions). The owner can always read the card text on the card, whatever the parser made of it |
| `collected_at` is set only if the Telegram profile part succeeded; a failed photo or Leomatch part does not block it | Without it the startup sweep retries the contact. Bio and nick are the core of the card; the photo and the matching-bot text are extras that are not worth an endless retry |
| A startup sweep processes contacts in status `new` without `collected_at` before the first event | Events are best-effort and in memory; the database is the source of truth. The sweep repairs lost events and retries failed contacts |
| `ContactRepository.update_identity` refreshes `username` and `display_name` from the fetched profile | CYR-10 writes them once from the first message, which can be stale or missing; Telegram is the source of truth |
| The photo is saved as `profiles/<internal contact id>.jpg` under `MEDIA_DIR` through a `.part` file, and the profile stores the path relative to `MEDIA_DIR` | A name made from the Telegram id or a name would put personal data into file listings and backups; a relative path survives a changed `MEDIA_DIR` and the move between the host and the container; the rename leaves no half-downloaded photo |
| The collector never sleeps or retries on a flood wait: the adapter maps every Telegram failure to `ProfileSourceError` and that part fails | The sweep or the next event retries later; a sleeping collector would hold the whole queue. Telethon itself still waits out short flood waits inside one call (its `flood_sleep_threshold`, 60 s by default); the 30 s budget cancels such a wait |
| The matching-bot lookup is read-only: server-side search for the username (bare and with `@`, at most 5 results each), then a local scan of the last 100 messages; the newest message that passes the strict check is the match message | Searching is cheap and precise when it works; the scan is the fallback, and the only method without a username. No write method is used and nothing is marked as read |
| The strict match check accepts a user-mention entity with the contact's Telegram id, a `tg://user?id=` link, a `t.me/<username>` link or a standalone `@username`; comparison is case-insensitive and word-boundary aware; evidence by id beats evidence by username, and a message that names another user id never matches by username | `ann` must never match `joanna`, `ann_k` or `ann2`. A match message for someone else is worse than none: the owner would see a stranger's text on the card |
| The card is looked for at most 2 positions before the match message, in the last `CARD_HISTORY_LIMIT` (15) messages before it; outgoing positions and positions without text or caption are skipped; the first incoming position with text is the card, and the walk stops there; a position in which any message has a user mention, a `tg://user` link or a `t.me/` link ends the walk without a card | Two chain shapes exist (card, like, match and card, match). Never take two cards, never take someone else's. Reading 15 messages is enough for two albums of up to 3 plus the like |
| An album (consecutive messages with the same non-null `grouped_id`) is ONE position; any other message is a position of its own. The card text is the first non-empty caption among the messages of the position, ordered by message id | The matching bot sends a card as one message group: up to 3 photos with the caption on one of them, or one video with a caption. Counting each message as a position ran out of the two positions on captionless photos, so the text was missed and only one photo could be stored. The caption position inside an album is not observed, so any message may carry it |
| Observed on a real match (CYR-30). Card message: a header paragraph ending with a colon, a blank line, then `Name, age, City` with no description. Match message: a congratulation, a blank line, then `Начинай общаться 👉 <name>` where the name is a user-link entity and the person has no public username | Replaces the format that CYR-11 assumed. The texts are the matching bot's own wording, with an invented name in fixtures |
| The parser skips a first paragraph that ends with a colon when at least one more non-empty paragraph follows; it does not whitelist the header wording. The description is optional (`about` stays empty without it); `Name, age`, `Name, age, City` and `Name, age, City <dash> description` are accepted, the dash being a hyphen, en dash or em dash with whitespace on both sides, so `Санкт-Петербург` is not split. Age 18 to 99, emoji in the name allowed. A text that does not match keeps only `raw_text` | The header wording may vary with the bot's version; a colon plus a following paragraph is the structure that was observed. Requiring whitespace around the dash is what keeps hyphenated cities whole |
| The match message is found by the user-link entity with the contact's Telegram id even when the contact has no username; confirmed live | Resolves the earlier worry that a contact without a username could not be matched. Evidence by id was already the strongest evidence |
| The card photos are stored separately from the profile photo: `profiles/<internal contact id>-card-<n>.jpg` (n from 1) through a `.part` file, relative paths in the list `leomatch.photos`, at most `MAX_CARD_PHOTOS` (5); the Telegram profile photo stays in `photo`. Each is a read-only `download_media` of one message of the card position (a read member of the client Protocol, no new request class) | The owner sees the pictures the matching bot showed next to the card text, which may differ from the profile photo. Reading a message's media sends nothing and marks nothing as read. The names carry the internal id and a number, never a Telegram id or a name |
| A video message of a card has no photo and is never downloaded; a card that is a single video still gives its caption text and no photos | Video size and the download time are not worth the 30 s budget; the caption is what the owner needs to decide |
| The card photos are their own collection part (`card_photos`): one failing photo never blocks the others, another part or the ready event; a photo whose download fails keeps the old path at its index, and the stored list never shrinks because of a failed attempt or a card with fewer photos | Same reasoning as for the other parts; a photo gathered once is not thrown away by a later failure |
| `LeomatchSource.find_texts` returns a `LeomatchLookup`: the card text, the match text, the name under the link to the contact in the match message, and an optional `CardPhotos` handle (`count`, read-only `download(index, destination)`) | The collector learns from one lookup what the card says and how many photos it has, and can download them, without a second search in the matching-bot chat |
| When no card text was found, or it did not parse, the name is the text covered by the user-link entity of the match message whose user id is the contact's Telegram id (a `MessageEntityMentionName`, or a `tg://user?id=<id>` URL entity), not the wording around it; `name_source` says `card` or `match`; a parsed card name always wins; the name is sanitized and truncated like other texts | The observed match message ends with `Начинай общаться 👉 <name>` where the name is the link, so the entity text is the one reliable place for it. Age, city and about are never taken from the match message |
| Old contacts keep their old stored shape; only newly collected ones get the new one. `LeomatchProfile` reads the legacy single `photo` key as a one-item `photos` list, ignores the legacy `related_texts` key, and treats a legacy `name` without `name_source` as a card name. No database migration | The JSONB profile is read through a tolerant model, so old rows keep working. A legacy `raw_text` that was a match text (the old fallback) stays as it was written and is shown as card text, because the collector does not re-collect contacts that already have `collected_at` |
| New setting `LEOMATCH_BOT_USERNAME`, default `leomatchbot`; timeouts and limits are constants, not settings | The default is a guess to check in Telegram. Limits change with the code, not per deployment |
| The session is created by `python -m cyrano login` (`make login`, `make login-docker`); phone, code and password are asked, passed on and never stored or logged; the phone is asked before any network call; the file gets mode `0600` | The session file is a secret that controls the second account. Asking first lets the owner abort without any network traffic |
| Dependency added for the control bot: `aiogram` 3.x (3.31.0 at the time of CYR-12), imported only inside `bot/`; it ships type information, so mypy needs no override. Adding it lowered pydantic from 2.14.2 to 2.13.5 in `uv.lock`, because aiogram requires `pydantic<2.14` | Agreed for CYR-12; it works on Python 3.14. The pydantic pin is aiogram's, not ours; it can move up with aiogram |
| The card is shown on the `ContactReadyEvent` whether or not the collection succeeded, and a card for a profile that was not collected says so | The ready event already means "finished, successfully or not". The owner decides from what is known; a failing Telegram profile must not hide a person who wrote |
| The announcer sweeps once at start and then every `CARD_SWEEP_INTERVAL` (120 s); a `new` contact is swept when its profile has `collected_at` or is older than `CARD_WITHOUT_PROFILE_DELAY` (600 s) | Events are best-effort and in memory; the database is the truth. The 600 s rule means a collector that keeps failing never keeps the owner waiting, and a contact whose event was lost is found within two minutes. The sweep also retries cards that failed to send (the owner has not pressed Start, a flood wait) |
| Send the card first, set `new -> pending` only after the sender returned `True`; duplicates are tolerated because the callbacks are idempotent | The opposite order loses a card when the send fails after the status changed, and a lost card means an unanswered person the owner never sees. A duplicate card costs one extra message |
| One consumer handles contact ids strictly one at a time; the event feed and the sweep only enqueue ids, and an id already queued is not queued twice | Gentle on Telegram limits and in order for the owner; no concurrent sends for the same contact |
| Photos are sent before the text card; the buttons live on the text message; the profile photo first, then all card photos, go as ONE media group (a single photo uses `send_photo`) with a caption on the first item only: «Фото профиля и анкеты», «Фото профиля» or «Фото анкеты», chosen from the readable photos that remain | A media group cannot carry an inline keyboard. The text message is the one the owner acts on and the one that is edited after the decision. Telegram shows only the caption of the first item of a group. With at most 1 + 5 photos the group stays below Telegram's limit of 10 items |
| A `BadRequest` on the photo step other than "chat not found" skips the photos and still sends the text card; every other Telegram API error returns `False` | A photo that Telegram permanently rejects would otherwise block the contact on every sweep forever. The owner still gets the card, and the skip is counted |
| `TelegramRetryAfter` is waited for up to 60 s and retried once; a longer wait or a second one returns `False` | The sweep is the retry loop. The announcer is strictly sequential, so a long wait would hold every later card; giving up lets the sweep try again in two minutes |
| Polling runs inside the app process as a task with `handle_signals=False`; our own SIGTERM and SIGINT handling stays in charge | One process, one shutdown order, one signal path (CYR-10 already has the tests for it). aiogram's own handlers would compete with ours |
| A rejected token or an unexpected end of polling is a fatal, readable error with a non-zero exit; the owner not having pressed Start is not | A wrong token is fixed by the owner and the restart policy shows it at once. Not having pressed Start is also fixed by the owner, but needs no restart: sends fail softly and the sweep delivers the waiting cards after the owner presses Start. Limit: aiogram retries failing `getUpdates` calls forever, so a token revoked while running is not noticed |
| The control bot drops updates from anyone but `OWNER_TELEGRAM_ID` in an outer middleware on every update type, silently | S8: nobody else gets an answer, a side effect, or a hint that the bot exists. Covering all update types is stricter than messages and callbacks only and costs nothing |
| `CardActions` outcomes: `applied`, `already_applied`, `refused`, `not_found`, `mode_unavailable`; a card shows the CURRENT state of the contact, and actions run one at a time under a lock | Buttons on old cards are stale by nature. Showing the current state keeps the owner's picture true, and the repository has no compare-and-set, so the lock keeps a reply and an ignore from racing inside the process |
| Ignore is refused on an `active` contact, and Reply with another mode is refused on an `active` contact, even though the transition matrix allows `active -> ignored` | The matrix is for deliberate actions; a stale card must never undo a decision or re-mode a contact the autopilot is already talking to. Pause, resume and ignore for `active` contacts need their own entry point (open question) |
| Card texts are truncated to named limits (`domain/models.py`) and assembled in sections within a 3500-character budget; a section that does not fit is left out whole | Telegram refuses a message over 4096 characters; leaving out a whole section never cuts an HTML entity in half |
| Dependency added for the LLM client: `httpx` (0.28.1 at the time of CYR-13), imported only inside `llm/`; tests use `httpx.MockTransport`, no `respx`. No provider SDK | Agreed for CYR-13; it installs and imports on Python 3.14. Plain HTTP keeps the provider replaceable and the transport fakeable |
| The `LLMClient` Protocol lives in `services/llm_client.py`; models in `domain/llm.py`, errors in `domain/errors.py`; the DeepSeek implementation, transport and factory in `llm/`, which does not import `services` | Consumers see only the interface, the domain types and the domain errors. The LLM message class is `LLMMessage` because `domain.models.Message` is the stored chat message |
| The client is not wired into `main.py` yet; only `llm-check` builds the factory | No consumer exists. CYR-16 and CYR-17 will build it in the composition root |
| JSON comes from a schema instruction plus validation, with the provider's JSON mode as an addition: a system message with the model's JSON Schema after the caller's leading system messages, `response_format: {"type": "json_object"}`, then `model_validate_json` on a fenced block or the whole reply | Works with any provider; validation, not the model, decides what is valid. The provider documents that JSON mode needs the word JSON in the prompt, which the schema message provides |
| An invalid JSON reply is sent back as an assistant turn plus a user turn listing field paths and messages (never input values), asking for a shorter output when truncated; a blank reply is retried unchanged; the first call plus `LLM_JSON_MAX_RETRIES` (2) retries, both failure kinds sharing that budget | Gives the model what it needs to fix the reply without echoing data into the correction. The provider documents that JSON mode can return only spaces. "Every attempt counts against the constant" is read as: 1 call + 2 retries, so at most 3 calls |
| The raw invalid reply never leaves the `llm` package: the final `LLMInvalidResponseError` carries only the attempt count and has no cause; the warning logs carry counters | The reply is personal data (S9) and may echo the prompt |
| Retry policy: network errors, 429 and 5xx, up to 3 retries, backoff 1 s doubling to a 30 s cap with jitter lowering the delay by up to half; `Retry-After` (seconds or HTTP date) replaces the backoff and a value above the cap fails at once; other 4xx never retried | Transient failures should not lose a reply; a provider that asks for more than 30 s is better reported than waited for inside a request path. The DeepSeek documentation does not mention `Retry-After`, so honouring it is the standard HTTP behaviour, not a documented one |
| Every attempt has a hard 60 s deadline (`asyncio.timeout`), a miss counts as a network error; the http client also has connect, read, write and pool timeouts | A provider can hold a connection open without answering (DeepSeek documents that it keeps non-streaming requests open with empty lines for up to 10 minutes while it waits to start inference). Replies are short (400 and 1500 tokens by default), so 60 s is generous |
| Exceptions and logs carry the status code or the exception class only, never response bodies, message texts or the key; the key is set once as the `Authorization` header of the shared http client; no httpx exception leaves the package | Bodies and prompts can contain personal data and echo the key; S9 |
| Thinking is sent explicitly as `thinking: {"type": "disabled"}` unless `DEEPSEEK_THINKING=true` | Confirmed in the DeepSeek documentation: the parameter is `thinking` with `type` `enabled` or `disabled`, and thinking is on when it is omitted. A chat reply must not spend tokens on reasoning, and `temperature` has no effect in thinking mode |
| Per-step settings, all optional with defaults in code: `DEEPSEEK_BASE_URL` (`https://api.deepseek.com`), `LLM_REPLY_MODEL` and `LLM_SUMMARY_MODEL` (default `DEEPSEEK_MODEL`), temperatures 1.0 and 0.2, max tokens 400 and 1500. Temperature outside 0..2, non-positive tokens, a blank model and a non-http(s) base URL are rejected with the readable `ConfigError`. `.env.example` is unchanged | A reply wants variety and a short answer, a summary wants precision and room. The step defaults are guesses to tune with real replies |
| `max_tokens` is always sent: the per-call value, else the step default | An unset limit would fall back to the provider's default (8K, or far more with thinking), which is too long for a chat reply |
| `llm-check` sends a tiny request with `max_tokens=5` and prints the model, the token counts and the latency, never the reply; an `LLMError` prints the class and message and exits 1 | A one-off proof that the key, the model name and the network work, for the owner to run once with a real key |
| The model and base URL settings are in the startup log line allowlist (models, temperatures, max tokens, thinking), the base URL is not | None of them is personal; a base URL may carry credentials |
| The persona and the style examples are imported by a command and stored in PostgreSQL; the runtime reads them from the database, never from a file path. This differs from the ticket text, which read the persona from a path | The app and worker run in containers that cannot see the owner's files, and a path setting would have to be mounted and kept in step with the database. One source of truth in the database works the same locally and in Docker, and is read with the repositories the rest of the code already uses |
| The import runs as a local command (`python -m cyrano persona import FILE`, `examples import FILE`, `make persona-import`, `make examples-import`), with the app `Settings` and the host database port, like `make migrate`. It is not part of `main.run`, and `run` does not build the persona or example services yet | Importing is an owner action on owner files, done rarely. Nothing consumes the data until the prompt builder (CYR-16), so wiring it into the app now would be dead code |
| The persona is free text or Markdown, 1 to 8000 characters after trimming, with no required structure; the suggested sections (who I am, interests, humor and tone, facts that must stay consistent, things I never say) are advice in [persona-and-examples.md](persona-and-examples.md), not validation | A structure imposed by code would make style changes a code change. The limit keeps the persona a small fixed share of the prompt |
| The examples file is JSON `{"version": 1, "dialogues": [{"tags": [...], "turns": [{"role": "me" or "them", "text": "..."}]}]}`. `tags` is optional (missing or empty means generic, usable by every mode). Unknown keys are refused; so are empty texts, an unknown role and a version other than 1 | A versioned, closed format is checked completely and can grow without silently ignoring a misspelled key. Tags are mode names, so they match the modes of CYR-15 |

| The outbox is a PostgreSQL table (`scheduled_messages`), and sending happens in the app process; a future worker (CYR-17) only generates replies and writes rows | The Telethon session lives in the app. Answers the earlier question of how the worker sends: it does not. | `OutboxSender` is the only caller of `send_text`, and `TelethonAdapter` the only module with a Telethon write call; structural tests scan all of `src` | Guards, limits and pacing can only be trusted if they cannot be bypassed (S2). | Sending is strictly sequential: one row at a time, one row per 2 s poll | Gentle on Telegram limits, and the volume is low. Humanization (CYR-18) has one place to go, as the limits (CYR-22) had |
| A row is claimed by `FOR UPDATE SKIP LOCKED`, one at a time, ordered by `send_at` then `id`, and set to `sending` in the same transaction | Two claimers can never get the same row, even if a second loop ever appears |
| A row left in `sending` is never sent again: the startup sweep and the stale check (older than 120 s, every 60 s) mark it `failed` with `interrupted` and notify the owner once. Each send has a 100 s deadline, shorter than the stale age; past it the row fails as `uncertain` at once | Nobody can know whether a stuck send reached Telegram. A lost message is visible and the owner can act on it; a duplicate message to a person cannot be taken back |
| A failure of `complete_send` after a good send is not retried; the row stays `sending` and the stale check fails it | The send cannot be repeated, and a retry loop on storage would hold the sequential sender. The owner is told and reads the chat |
| The guard runs at enqueue and again right before sending, on a freshly read contact; a refusal at send time cancels the row with the reason | Statuses change while a row waits (locked decision). Refusing at enqueue also keeps wrong rows out of the table |
